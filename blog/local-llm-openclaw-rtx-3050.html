From Cloud Throttling to a Home Server: Self-Hosting OpenClaw with a Local LLM on an OptiPlex 990

Richie Richard Rajkumar · May 2026 · 18 min read

I wanted a personal AI assistant on Telegram. The kind that lives in my pocket, accepts a casual "summarise the Hacker News front page" at 11pm, helps me triage a Trello board on a tram ride, opens a GitHub PR for a blog draft I described in two sentences. Self-hosted, my data, no quotas. The plan was simple: pick a cloud LLM provider, point OpenClaw at it, pair Telegram, done.

Three free tiers and one humbling weekend later, I learned that free-tier cloud LLMs are not built for heavy agent clients. OpenClaw pushes ~46K tokens of system prompt, identity manifest, and MCP tool definitions before my first character arrives. Gemini's free tier rationed me to one conversation a day. Groq's tokens-per-minute ceiling rejected the very first turn. DeepSeek's "$5 free credit" landed in my account as a flat $0.00.

The fix turned out to be a 2011-vintage Dell OptiPlex 990 sitting unused in a cupboard, a €260 low-profile RTX 3050 with 6GB of VRAM, and a careful walk through three models before qwen2.5:7b-instruct earned its place as the household chat model. This is the long version of that story: why the cloud failed, what hardware I picked and why, how Gemma 4 E2B refused to call tools, and why Qwen 2.5 at Q4 turned out to be the sweet spot.

A Quick Glossary Before We Start

This post uses a fair amount of LLM-stack jargon. If any of the names below are unfamiliar, here is the one-line version of each.

Term What it is
LLM Large Language Model. A neural network trained on text that can chat, summarise, code, and (with the right plumbing) call tools. ChatGPT, Claude, and Gemini are all LLMs.
Ollama An open-source runtime that downloads, loads, and serves LLMs on your own machine. Think "Docker, but for language models". You run ollama pull qwen2.5, it fetches the weights, and exposes an OpenAI-compatible API on localhost:11434.
OpenClaw A self-hosted AI assistant framework. It wraps an LLM with a personality file, persistent memory, a tool registry (via MCP), and a set of chat channels (Telegram, Slack, web). The "body" around the model's "brain".
MCP Model Context Protocol. An open spec from Anthropic for exposing tools (web search, GitHub, Trello, file systems) to LLMs in a consistent way. An MCP server publishes tools; an MCP-aware LLM calls them. Think "USB for AI tools".
Gemma 4 E2B Google's small open-weights model. "E2B" is the Edge 2B-parameter variant, sized for phones and low-VRAM devices. Fast, but too small for reliable agentic tool calling (as we'll see).
Qwen 2.5 Alibaba's open-weights model family. We use two variants: qwen2.5:7b-instruct (general chat + tool use) and qwen2.5-coder:7b (code-tuned, for the blog-writer agent). Both are 7B parameters and fit 6GB of VRAM at Q4 quantization.
Gemini 2.5 Flash Google's cloud-hosted small-fast LLM. Free tier of 20 requests/day on the public API. We hit a wall with it (see below) but keep it around for one specific job.
Groq (Llama 3.3 70B) Groq is a cloud inference provider built around custom LPU chips that serve open-weights models (like Meta's Llama 3.3 70B) at very high tokens/sec. Free tier is generous on requests but capped at 6,000 tokens/minute.
DeepSeek A Chinese AI lab and cloud LLM provider. Cheap on paper, but the "$5 free credit" promotion I tried turned out to be expired.
Quantization / Q4 Compressing a model's weights from 16-bit floats to fewer bits to shrink VRAM and disk footprint. Q4 ≈ 4 bits per weight. A 7B model at FP16 is ~14 GB; at Q4 it's ~4.5 GB, with only a small drop in quality.
VRAM Video RAM, the dedicated memory on a GPU. The single most important number when choosing hardware for local LLMs. Model weights + KV cache + driver overhead all compete for this pool. 6GB is the practical floor for running a 7B model entirely on the GPU.
KV cache The "key/value" cache, a chunk of GPU memory that stores attention state for the conversation so far. Grows with context length. A 7B model at 8K context burns ~1 GB just on KV cache.
Telegram / Trello / Brave Search / GitHub The four external services this assistant wires together. Telegram is the chat front-end, Brave Search is the web-search MCP, GitHub is for repo/PR operations, Trello is the kanban board it reads for blog topics.

With those out of the way, the story.

The Goal: An AI Assistant That Lives on Telegram

OpenClaw is a self-hosted AI assistant: think of it as a thin Docker-Compose gateway that wraps a model with a personality file, persistent memory, an MCP (Model Context Protocol) tool registry, and a set of channels (Telegram, Slack, web). You message it, it routes the message through the model with all your registered tools available, and replies in the same channel. The MCP layer is where it gets useful: my gateway registers brave-search (web), github (issues, PRs, files), and trello (boards, lists, cards). The model can call any of them mid-conversation.

The whole thing is provisioned by an Ansible playbook (Docker, Ollama, OpenClaw, Telegram pairing, identity files, the lot). The intent was to keep the Ubuntu AI server reproducible from zero, so if I ever wipe it, one command rebuilds the entire stack. With that part settled, the only open question was which model to point it at.

The architectural premise: Cheap, ubiquitous LLMs make personal AI assistants finally interesting. The model is the brain, MCP servers are the hands, OpenClaw is the body. The thing that turns out to matter most is whether the brain you picked can survive the bill at the end of the month.

Attempt 1: Just Use the Cloud

The original config pointed OpenClaw at Google's gemini-2.5-flash. I picked it for three reasons: a decent free tier on paper, strong tool-calling reputation, and the only provider with an OpenClaw integration ready out of the box. Then I onboarded the assistant.

Gemini 2.5 Flash: One Conversation a Day

OpenClaw's onboarding flow is conversational: it interviews you to draft an IDENTITY.md, a SOUL.md (assistant personality), and a USER.md (your profile and working style). Each of those interviews is a multi-turn exchange. By the time my assistant had a name (Shruthi), a personality, and knew I worked in Berlin, I had used 18 of my 20 daily free-tier requests. The remaining two went to "hello" and an attempted Trello query, after which the bot replied with the most disappointing error you can read at 10pm on a Sunday:

// Gemini API response
{
  "error": {
    "code": 429,
    "message": "Quota exceeded for quota metric 'Generate Content API requests per day'",
    "status": "RESOURCE_EXHAUSTED"
  }
}

That's the trap with daily quotas: they aren't billed as "fair use" the way RPM ceilings are. They reset at midnight Pacific time, and once you've burned the day, you have a brick on Telegram until tomorrow. For an assistant the entire point of which is being available when I need it, that's a non-starter.

Groq + Llama 3.3 70B: TPM Cliff at Turn One

Groq's free tier looked friendlier on the spec sheet: unlimited daily requests, no per-day quota, just a tokens-per-minute ceiling. I switched OpenClaw's provider to Groq and pointed it at llama-3.3-70b-versatile. First Telegram message: "list my open GitHub issues". Response:

HTTP 429
{
  "error": {
    "message": "Rate limit reached for model 'llama-3.3-70b-versatile' in organization. Limit 6000 TPM (tokens per minute). Used 46812. Please try again in 7m 48s.",
    "type": "tokens",
    "code": "rate_limit_exceeded"
  }
}

This is the punchline that took me a minute to absorb. The system prompt + identity files + persistent memory + ~80 MCP tool schemas add up to roughly 46,000 tokens before my own message is even appended. The free tier's ceiling was 6,000 tokens per minute. A single OpenClaw turn doesn't fit in eight minutes of quota.

That's the structural mismatch nobody warns you about. Free tiers are designed for "send a small prompt, get a small reply" chatbot traffic. They are not designed for an agent that boots up carrying its entire personality and toolset every turn. The arithmetic just doesn't work.

DeepSeek V4 Flash: The Phantom Credit

I tried DeepSeek next, lured by the "$5 free credit on signup" line on their landing page. Account created, key generated, OpenClaw repointed. First request:

HTTP 402 Payment Required
{
  "error": {
    "message": "Insufficient balance. Top-up required to make requests."
  }
}

I checked the dashboard. Account balance: $0.00. The "$5 free credit on signup" line was, charitably, marketing for a promotion that had ended. There was no inline notice that the offer was over; you only learn after creating the account and trying to actually call something. Pay-as-you-go from minute one is fine for a business workload, but for a personal experiment where I wanted to see whether the architecture even worked before committing money, it was a hard no.

The Pattern, Across All Three

Provider Free-tier limit How OpenClaw breaks it
Gemini 2.5 Flash 20 req/day Onboarding alone takes 15–18 turns. Day one is gone before the first real question.
Groq (Llama 3.3 70B) 6,000 TPM System prompt + MCP tool definitions ≈ 46K tokens. Single turn cannot fit.
DeepSeek V4 Flash $5 signup credit (advertised) Balance is $0 on first call. Pay-as-you-go from minute one.

And these are just the limits I hit. The wider catalogue of cloud-provider tax that bites you eventually: regional access pauses (Gemini is region-gated for some EU postcodes), model deprecations (the 70B you tuned for today may be removed in a quarter), TOS changes for free tiers, and the small matter of every prompt, every tool result, every personality file being sent to a third party. For an agent that knows my Trello, my GitHub, and my calendar, "where my data goes" is not a footnote.

The realisation: Cloud LLMs are priced and rate-limited for chatbots that send 500-token prompts. They are not priced for agents that ship a 46K-token bootstrap context every turn. Free tiers actively punish the agentic shape of work. The only way to win is to stop playing.

The Machine: A Dell OptiPlex 990, Resurrected

I had been quietly assuming a self-hosted LLM meant buying a Mac Studio or building a fresh PC with a 3090. Both would have cost thousands. The actual right move was already in my cupboard.

The Dell OptiPlex 990 SFF (Small Form Factor) is a 2011-era business desktop, the kind that runs spreadsheets at law firms and gets replaced every five years. Mine had been my home media box from 2014 to 2017, then sat unpowered since. Specs:

Component Spec Relevance to LLM serving
CPU Intel Core i7-2600 · 4 cores / 8 threads · 3.4 GHz (Sandy Bridge, 2011) Plenty for OS, Docker, OpenClaw gateway. Token generation will run on GPU.
RAM 16 GB DDR3 (chipset max) Generous for a 7B model loaded mostly on GPU; OS + Docker + Ollama fits comfortably.
Storage 500 GB SATA SSD Each Ollama model ≈ 4.5 GB on disk. Two models + OS + Docker images fits easily.
PSU 240W (fixed, proprietary form factor) The constraint. Any GPU must be ≤75W slot-powered. No 6-pin or 8-pin connectors available.
Expansion 1× PCIe 2.0 x16, SFF chassis = low-profile cards only The second constraint. Only LP GPUs physically fit.
OS Ubuntu 24.04 LTS Server NVIDIA drivers available via apt; Ollama and Docker both first-class.

The use case I had in mind shaped what I needed from the machine. It would sit on a shelf, 24/7, mostly idle, occasionally answering a Telegram message in 10–25 seconds, and once a day running a longer blog-writing job for ~5 minutes. Not a workstation for interactive coding. Not a real-time chatbot for hundreds of users. A personal back-office. For that workload, a 13-year-old quad-core was wildly overpowered for the CPU side, and the entire game was about getting a usable GPU into a slot designed for office work.

The GPU Upgrade: A Low-Profile RTX 3050 with 6GB of VRAM

This is the single decision that made the project viable. Two hard constraints from the OptiPlex 990 SFF chassis:

  1. Low-profile only. The card has to be physically short, with an LP bracket. Most consumer GPUs are full-height.
  2. ≤75W total power. The 240W PSU has no 6-pin or 8-pin PCIe power leads available. The GPU has to draw its entire budget from the PCIe slot, which caps at 75W.

Add a third soft constraint: enough VRAM to run a 7B model at Q4 quantization with KV cache headroom. Below 6GB, you're stuck at 3B or smaller. Above 6GB on an LP 75W card, options thin out quickly.

The Candidate Shortlist

Card VRAM TDP Price (used / new, EU) Verdict
GTX 1650 LP 4 GB 75W ~€140 VRAM too small for 7B Q4. Would force 3B class and weaker tool calling.
RTX A2000 LP 6 GB 70W ~€420 Spec-perfect, but a workstation card priced like one.
RTX 3050 LP 6GB 6 GB 70W ~€260 LP, slot-powered, 6 GB VRAM. The cheapest card that meets all three constraints.
RTX 4060 LP 8 GB 115W ~€350 Exceeds 75W slot power. Would need a 6-pin lead the 240W PSU cannot supply.

The 6GB RTX 3050 LP is a slightly unusual SKU: most 3050 LP cards ship as 8GB / 115W variants. The 6GB / 70W variant exists specifically for SFF and low-power-budget builds, sold by MSI, PNY, and Gigabyte under near-identical naming. It is the sweet-spot card for resurrected office desktops, which is exactly what I had.

Why 6GB is the Magic Number

This took me a few hours of reading to internalise. The number you care about for running an LLM locally is the quantized model footprint + KV cache + runtime overhead, all of which compete for the same VRAM pool. Rough math for a 7B model at Q4 quantization:

  • Weights on disk: ~4.0–4.5 GB (Q4_K_M is the Ollama default; you'll see this number when you run ollama show qwen2.5:7b-instruct).
  • KV cache: grows with context length. For a 4K context window with a 7B model at FP16 KV, expect ~500–800 MB. OpenClaw runs with ~8K effective context, so budget more like 1.2 GB.
  • CUDA / driver overhead: 200–400 MB resident regardless.

Total for a 7B Q4 model with realistic context: ~5.5–6.0 GB. A 6GB card sits right on the edge, with a few hundred megabytes of headroom. Anything bigger (8B, 13B) overflows the VRAM and Ollama starts paging layers between GPU and CPU. The moment that happens, your tokens-per-second collapses from 30 to about 3, and a normal chat turn that took 12 seconds takes 90.

So the question "why 6GB?" has a clean answer: 6GB is the smallest VRAM that lets the 7B model class fit entirely on the GPU. 7B is the smallest model class that does multi-tool agentic work reliably. The two numbers meet at one card, and that card has to be LP and slot-powered. There were maybe three SKUs that fit, and the 3050 LP 6GB was the cheapest.

The math one level up: VRAM budget = model weights + KV cache + driver overhead. Pick your model first, then size the GPU to match. People who pick the GPU first and then "see what runs" almost always end up with a 4GB card and a 3B model that hallucinates tool calls.

Physical Install

The install itself was uneventful, which is the highest praise hardware projects deserve. Powered down, opened the SFF chassis, removed the LP slot cover, slotted the card, screwed in the LP bracket, closed up. No PSU upgrade needed: the RTX 3050 LP 6GB pulls 100% of its power through the PCIe slot, which the OptiPlex's 240W PSU supplies cleanly.

On Ubuntu 24.04, the driver path was equally calm:

# Add the graphics drivers PPA (Ubuntu's official one)
sudo add-apt-repository ppa:graphics-drivers/ppa
sudo apt update

# Install the recommended driver. As of May 2026, 565-server is current.
sudo apt install nvidia-driver-565-server

# Reboot, then confirm
sudo reboot
# after login:
nvidia-smi

The entire box, idle most of the day with brief inference spikes, averages ~80W and costs about €20/month in electricity. That's the floor of what this kind of hosting costs you, and it's pleasantly small.

Ollama: The Inference Runtime

With the GPU in place, I needed an inference server that could load a model into VRAM and expose an OpenAI-compatible API on the local network. Two real choices in May 2026: Ollama and llama.cpp's server. I picked Ollama for three reasons: a clean systemd integration, the model-pull/registry workflow ergonomically similar to Docker (ollama pull qwen2.5:7b-instruct), and an OpenAI-compatible API surface OpenClaw can talk to with one config line.

The Ansible role for it is twenty lines, the meaningful bits being:

# roles/ollama/tasks/main.yaml (abridged)
- name: Install Ollama
  ansible.builtin.shell:
    cmd: curl -fsSL https://ollama.com/install.sh | sh
  when: ollama_check.rc != 0

- name: Bind Ollama to all interfaces (so Docker containers can reach it)
  ansible.builtin.copy:
    content: |
      [Service]
      Environment="OLLAMA_HOST=0.0.0.0:11434"
    dest: /etc/systemd/system/ollama.service.d/override.conf

- name: Pull configured models
  ansible.builtin.command:
    cmd: "ollama pull {{ item }}"
  loop:
    - qwen2.5:7b-instruct
    - qwen2.5-coder:7b

The OpenClaw container reaches Ollama through Docker's host bridge:

// openclaw.json · provider config
"providers": {
  "ollama": {
    "baseUrl": "http://host.docker.internal:11434/v1",
    "apiKey": "ollama",
    "timeoutSeconds": 300,
    "models": [
      { "id": "qwen2.5:7b-instruct", "name": "Qwen 2.5 7B Instruct" },
      { "id": "qwen2.5-coder:7b", "name": "Qwen 2.5 Coder 7B" }
    ]
  }
}

Why bare-host Ollama instead of containerised? Three reasons: GPU passthrough into Docker is fiddly on consumer NVIDIA drivers (the nvidia-container-toolkit dance works but adds a layer of "why is it slow today" debugging), the host has nothing else competing for the GPU, and rolling Ollama updates is a one-liner (curl | sh) vs. rebuilding a custom image. Anything that talks to the GPU runs on the host. Everything else (OpenClaw gateway, MCP servers, the Docker networking around them) runs in containers.

The Model Journey: Gemma 4 E2B → Qwen 2.5 7B

This is the part I expected to be easy and was, instead, the most interesting failure of the project. There are dozens of open-weights models you can pull with Ollama. The 6GB VRAM ceiling rules out most of them, but plenty fit. The question isn't "which model fits"; it's "which model can actually drive an agent".

Attempt 1: Gemma 4 E2B (the Edge Variant)

Google's Gemma 4 family ships in several sizes. The E2B ("Edge 2B") variant is the smallest, ~2B effective parameters, designed for phones and laptops. At Q4 it's about 1.8 GB on disk and loads into VRAM in seconds. I picked it first because: it's recent, Google-trained, and a 2B model on a 6GB card felt like leaving room for KV cache growth.

For pure chat, Gemma 4 E2B was great. Fast first-token latency (~1 second), tokens-per-second in the 60s on the 3050, perfectly competent for "summarise this paragraph" or "what's the syntax for a Bash for-loop".

For agentic work, Gemma 4 E2B was, generously, ambivalent. The first sign of trouble was when I asked the assistant to search the web for a Kubernetes 1.34 release note:

me ▸ can you search the web for the kubernetes 1.34 release highlights?
shruthi ▸ I tried, but the search tool is currently unavailable. You might want to check the Kubernetes blog directly.
me ▸ [checks OpenClaw logs] the brave-search MCP server is healthy and reachable from inside the container. why did you say it was unavailable?
shruthi ▸ I'm sorry for the confusion. The search functionality appears to be temporarily unavailable in this session.

The brave-search MCP server was, in fact, healthy. I had tested it manually. The model never issued a tool call. It just told me that the tool had failed, without ever trying. This is the failure mode known in the trade as a "hallucinated tool failure". The model has seen, in its training data, plenty of examples of agents reporting tool errors. When confronted with a tool it doesn't quite know how to invoke, it pattern-matches to the apology rather than the call.

Underneath, the cause is straightforward: at ~2B effective parameters, Gemma 4 E2B does not reliably format the JSON-shaped function-call output that OpenAI-style tool use depends on. It "knows" the tool exists, it "knows" what it should do, but the structural step of emitting a tool_calls object with the right schema is too much for the model. So it falls back to natural language and invents an excuse.

I confirmed this by enabling verbose tracing in OpenClaw. Across 20 turns where a tool call was the right answer, Gemma E2B produced a syntactically valid tool_calls object exactly zero times. Across the same 20 turns, Qwen 2.5 7B Instruct produced a valid call 19 times. That's not a quality gap; that's a capability gap. Below ~3B parameters, structured agentic output is unreliable. Above ~7B, it's the default behaviour.

The general rule I extracted: if your use case involves any MCP or function-calling beyond toy demos, do not go below 7B parameters. The smaller models are useful for chat, autocomplete, classification, and inference inside a constrained schema, but they are not reliable agent brains. The 7B threshold is approximate; it's where multi-step tool use stops being a coin flip.

Attempt 2: Qwen 2.5 7B Instruct (the Default)

Qwen 2.5 7B Instruct is Alibaba's general-purpose mid-size model. At Q4_K_M it's 4.4 GB on disk, ~5.5 GB resident with KV cache, and fits the 6GB card with a few hundred megabytes to spare. On the RTX 3050 LP I see ~25 tokens/sec generation throughput, ~5 second first-token latency on a cold load (the bigger model is slower to warm up than Gemma E2B), and reliable tool calling.

The same conversation as before, with Qwen swapped in:

me ▸ can you search the web for the kubernetes 1.34 release highlights?
shruthi ▸ [calling brave_web_search(query="Kubernetes 1.34 release highlights")...]
shruthi ▸ Kubernetes 1.34 ("Octarine") shipped on April 23, 2026. Key changes: Dynamic Resource Allocation graduated to stable, sidecar containers GA, structured authentication config GA, and pod-level resource specifications now beta. The release notes also flag the removal of the in-tree CSI migration shims for AWS EBS and Azure Disk that were deprecated in 1.30. Full notes: https://kubernetes.io/blog/2026/04/23/kubernetes-v1-34-release/

That is a perfectly normal agentic answer: the model decided a tool call was the right move, formatted the call correctly, the gateway executed it, the result came back, and the model summarised it. The same sequence Gemma E2B refused to attempt.

The interesting performance characteristic of Qwen 2.5 7B on this hardware is the shape of latency, not the average. The first turn after the model loads from disk takes ~10 seconds (cold KV cache, full prompt processing). Subsequent turns in the same conversation take 3–8 seconds because the prefix is cached. A long tool-use chain (web search ▸ summarise ▸ format) can take 30–45 seconds end to end because each tool round-trip adds another round of prompt processing. Compared to Gemini Flash's 1–3 seconds for the same chain, it's slower. Compared to "the bot is throttled until tomorrow", it's instant.

Attempt 3: Qwen 2.5 Coder 7B (for the Blog Writer)

The blog-automation agent is a special case. It's not interactive; it runs once a day on a Trello trigger, clones the blog repo, reads the existing posts to learn the voice, drafts a new article in HTML, opens a PR, and moves the Trello card. The work is structurally code: file edits, HTML scaffolding, git operations, GitHub API calls. For that, qwen2.5-coder:7b turned out to follow the multi-step instructions noticeably better than the general-purpose instruct variant, with the same VRAM footprint.

Both models can't live in VRAM at once on a 6GB card. Ollama hot-swaps: when the blog cron fires, it unloads the chat model, loads the coder model, runs the job, and the next chat turn pays a ~10 second penalty to reload the instruct model. That's a fair price for one cron run a day. If I had two models I wanted resident simultaneously, the next hardware upgrade is the obvious one (more VRAM), but I haven't needed it.

Where the Cloud Still Earns Its Place

Local-only isn't religion. The blog automation pipeline ended up two-stage on purpose. Stage 1 is the local Qwen Coder 7B running the writer agent, producing an HTML draft and opening a PR. Stage 2 is google/gemini-2.5-flash in the cloud, taking that draft and polishing it for prose quality, voice, and consistency with the existing posts on the blog. The reason is one of fit:

  • Local model strength: multi-step agentic tool use over a long-running job. The writer agent does ~30 tool calls (git operations, file reads, HTML edits, PR creation). Cloud Gemini reliably stalls on this prompt shape; the local model handles it fine.
  • Cloud model strength: prose quality on a single focused prompt. The reviewer agent does one task: read a diff and produce a better version. No long tool-use chain. Free tier handles it comfortably (one call per blog post, well within 20 req/day).

That's the shape of a sane hybrid: use local for unlimited, low-stakes, multi-step work. Use cloud free tier for high-stakes, focused, single-prompt work. The cloud is never the workhorse, only the editor. Free-tier quota is never a daily anxiety; the worst case is "the polish step didn't run today, the draft is fine on its own".

Ansible-Ising the Whole Stack

The reason this entire setup is reproducible from scratch in 30 minutes is that everything sits in an Ansible role tree. The Ubuntu AI server playbook bootstraps five roles in order:

  1. dotfiles: SSH keys, zsh, Oh-My-Zsh, Powerlevel10k, git config. The shell I expect.
  2. gnome-remote-desktop: RDP server with TLS, so I can remote in from my MacBook to do GUI debugging.
  3. docker: Docker CE + Docker Compose plugin from the official apt repo, user added to the docker group.
  4. ollama: install, configure as systemd, pull qwen2.5:7b-instruct and qwen2.5-coder:7b, bind to 0.0.0.0:11434.
  5. openclaw: render openclaw.json with all secrets from Ansible Vault, deploy Docker Compose, start the gateway, register MCP servers (github, trello, brave-search), wire Telegram, deploy the blog cron pipeline.

The single command:

ansible-playbook playbooks/ubuntu-ai-server-bootstrap.yaml \
  --ask-vault-pass --ask-become-pass

The "factory reset" path matters more than it sounds. When I broke something experimenting with model swaps (twice, for reasons I'd rather forget), the recovery was:

docker compose -f /opt/openclaw/docker-compose.yml down
rm -rf /home/richierichardrajkumar/.openclaw/*
# run the playbook from the Mac
ansible-playbook playbooks/ubuntu-ai-server-bootstrap.yaml \
  --ask-vault-pass --ask-become-pass

Eight minutes later the bot was back online, identity reloaded from the templates in version control. That's the value of provisioning the assistant the same way you provision production infrastructure: experiments are cheap because rollback is cheap.

What I Actually Learned

  1. Cloud free tiers are not built for MCP agents. The bootstrap context of a real agent (system prompt + identity + tool definitions) is 30–50K tokens before your first character. Free tiers are sized for chatbot traffic at one-tenth of that. The mismatch is structural, not seasonal.
  2. VRAM is the line, and 6GB is where it crosses a useful model class. Below 6GB, you're stuck at 3B and tool calling breaks down. Above 6GB, options open up. Pick the model class first, then size the GPU.
  3. Tool-calling capability scales with parameter count, not training recency. Gemma 4 E2B is newer than Qwen 2.5 by months, but the 2B parameter count is the bottleneck. Newer is not better. Bigger is, for this specific capability, the thing that matters.
  4. Old workstations are excellent LLM hosts. A 2011-era SFF desktop with a €260 GPU is a perfectly serviceable always-on inference server. CPU speed barely matters; the GPU does the work. PSU and chassis dictate the GPU options. Pay attention to those before the spec sheet.
  5. Hybrid local + cloud is the pragmatic answer. Don't kill the cloud entirely; shape the workload to fit each tier's strengths. Local for unlimited multi-step agent work; cloud free tier for focused single-prompt polish. The free tier is sustainable when you stop asking it to be the workhorse.
  6. Provision the assistant the way you provision production. An Ansible role tree turns "I broke my AI" from a weekend recovery into an eight-minute rebuild. Identity, personality, tool registry, all in version control.
  7. Latency is a non-issue for asynchronous chat. 10–25 seconds per turn on Telegram feels almost identical to 2 seconds on a web app, because I'm doing something else while I wait. Latency budgets are use-case-specific; if you're not building a real-time copilot, slow local inference is fine.

What's Next

The 6GB VRAM ceiling is the obvious bottleneck for ambition. The next reasonable upgrade is either a used RTX 3060 12GB (around €220 on the second-hand market and full-height, which means a different chassis) or an RTX A4000 16GB if I felt rich. With 12GB I could run a 13B model at Q4 (so, Qwen 2.5 14B or DeepSeek's smaller distillation), keep both chat and coder models resident simultaneously, or fit a longer context window for the blog writer. None of that is necessary today; everything I currently want to do works on the 6GB card.

The other thread I'm pulling on is moving from Telegram-as-frontend to a small web UI for richer rendering of code blocks and tool outputs. OpenClaw exposes a web channel; the missing piece is hosting it behind Tailscale so it's accessible from anywhere without exposing the gateway to the public internet. That's a weekend project, not a hardware decision.
