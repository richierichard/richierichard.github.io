Infracost for Terraform: Catching AWS Cost Surprises Before They Hit Production

Richie Richard Rajkumar · May 2026 · 11 min read

Most teams discover their AWS cost mistakes the same way: a monthly bill arrives, someone in finance circles a line item in red, and an engineer is sent spelunking through CloudWatch and Cost Explorer to find out which Terraform PR added the surprise. The cost was decided weeks ago, in a pull request, but nobody knew the price tag until the invoice landed.

Infracost closes that gap. It reads a Terraform plan, prices every resource against the AWS public catalogue, and emits a cost estimate before terraform apply ever runs. Drop it into GitHub Actions and every PR gets a comment showing the dollar delta: what your change adds or removes from the monthly bill. Cost stops being a quarterly surprise and becomes a review signal, like a failing test or a security scan.

The Problem: Cost Lags the Code

The standard cost workflow at most companies looks like this: an engineer writes Terraform, opens a PR, gets approvals on the technical changes, merges, and applies. Three weeks later, someone notices the bill went up. By then the architecture is in production, the on-call rotation has been changed, and rolling it back means a migration, not a revert.

The information needed to prevent that exists at PR time. The plan output already lists every resource being created. The AWS pricing catalogue is public. The only thing missing is the glue: a tool that joins them and posts the number where reviewers will actually see it.

The mental shift: Treat cost like security or correctness. Both shifted left over the last decade. Static analysis catches vulnerabilities at PR time, type checkers catch bugs at PR time. Cost is the next signal to move from end-of-month reports to inline review feedback.

What Infracost Actually Does

Infracost is a single Go binary plus a pricing service. You point it at a Terraform directory or a plan JSON file, and it returns a monthly cost estimate for the resources in scope.

Install and Connect

# macOS
brew install infracost

# Linux (one-liner)
curl -fsSL https://raw.githubusercontent.com/infracost/infracost/master/scripts/install.sh | sh

# One-time auth: registers the CLI with the free pricing API
infracost auth login

The pricing data lives in Infracost's hosted catalogue. The CLI sends a hashed query (resource type + region + size), receives prices, and computes the estimate locally. Your Terraform code and state never leave your machine. Only the resource metadata needed to look up prices does.

The Two Commands That Matter

infracost breakdown shows the total monthly cost for what your Terraform would create:

infracost diff shows what changes between the current state and the planned state. This is the one you run in CI:

That's the entire core API. Everything else (CI integration, policies, dashboards) is built on top of these two outputs.

AWS Resources It Understands

Infracost prices over 1,000 AWS resources. The ones you'll hit most often:

Category Covered Resources
Compute EC2 (on-demand, Spot, Reserved-aware), Auto Scaling Groups, EBS, Lambda, Fargate
Kubernetes EKS control plane, node groups, Fargate profiles, EKS extended support
Databases RDS (all engines), Aurora (incl. Serverless v2), DynamoDB (provisioned + on-demand), ElastiCache
Storage S3 (storage tiers + requests + transfer), EFS, FSx, EBS snapshots
Networking ALB, NLB, NAT Gateway, VPN, Direct Connect, CloudFront, Route 53, Transit Gateway
Messaging SQS, SNS, Kinesis, MSK, EventBridge
Observability CloudWatch (logs, metrics, alarms), X-Ray, OpenSearch
Edge & security WAF, ACM, Secrets Manager, KMS, GuardDuty, CloudTrail

The pricing model is split into two parts: fixed costs that Infracost can derive entirely from the plan (e.g., an EC2 instance running 730 hours/month is deterministic) and usage-based costs that Infracost can't know without you telling it (e.g., how many S3 PUT requests, how much Lambda invocation time, how many gigabytes of data transfer).

Usage-Based Estimates

This is where most first-time users get caught. Run infracost breakdown on a Lambda-heavy stack and the output cheerfully reports "Monthly cost depends on usage" for every resource that scales with traffic. The estimate is technically correct but useless. It tells you nothing about what you'll actually pay.

The fix is an infracost-usage.yml file that supplies the missing numbers:

# infracost-usage.yml
version: 0.1
resource_usage:
  aws_lambda_function.api:
    monthly_requests: 8000000
    request_duration_ms: 120

  aws_s3_bucket.uploads:
    standard:
      storage_gb: 2500
      monthly_tier_1_requests: 500000   # PUT, COPY, POST, LIST
      monthly_tier_2_requests: 2000000  # GET, SELECT

  aws_nat_gateway.az_a:
    monthly_data_processed_gb: 3000

  aws_dynamodb_table.sessions:
    monthly_write_request_units: 10000000
    monthly_read_request_units:  40000000
    storage_gb: 120

Feed it back in: infracost breakdown --path . --usage-file infracost-usage.yml. Now the estimate accounts for the variable costs that often dominate the bill: Lambda invocations, NAT Gateway data processing, DynamoDB request units, CloudFront transfer.

Where to get the numbers: CloudWatch metrics for the existing prod workload, Cost Explorer's usage breakdown, or the application's own metrics. The numbers don't need to be perfect; order-of-magnitude is enough to surface bad architecture decisions. A NAT Gateway processing 50 TB/month versus 500 GB/month is the same Terraform resource but a 100× cost difference.

GitHub Actions Integration

This is where Infracost becomes part of the development workflow. The official action runs infracost diff on every PR and posts a comment showing the cost delta. Reviewers see the dollar impact next to the code changes, and nobody has to remember to run the CLI locally.

The Minimum Viable Workflow

# .github/workflows/infracost.yml
name: Infracost
on:
  pull_request:
    paths:
      - '**.tf'
      - '**.tfvars'
      - 'infracost-usage.yml'

jobs:
  infracost:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
        with: { ref: '${{ github.event.pull_request.base.ref }}' }

      - uses: infracost/actions/setup@v3
        with: { api-key: '${{ secrets.INFRACOST_API_KEY }}' }

      # Baseline: cost of the base branch
      - run: |
          infracost breakdown --path=terraform/ \
            --format=json \
            --usage-file=terraform/infracost-usage.yml \
            --out-file=/tmp/infracost-base.json

      # Check out the PR branch and compute the diff
      - uses: actions/checkout@v4
      - run: |
          infracost diff --path=terraform/ \
            --compare-to=/tmp/infracost-base.json \
            --format=json \
            --usage-file=terraform/infracost-usage.yml \
            --out-file=/tmp/infracost.json

      # Post a sticky comment on the PR
      - run: |
          infracost comment github --path=/tmp/infracost.json \
            --repo=$GITHUB_REPOSITORY \
            --pull-request=${{ github.event.pull_request.number }} \
            --github-token=${{ github.token }} \
            --behavior=update

The --behavior=update flag is the important one. Without it, every push to the PR posts a new comment and the conversation thread becomes unreadable. With it, Infracost edits the same comment in place so reviewers always see the current state.

Cost Policies as Code

A comment is a nudge, not a guardrail. To actually block a PR (say, when someone tries to merge a $5,000/month change without an architecture review), you need policy enforcement. Infracost supports two approaches.

Built-In Threshold Checks

The simplest: fail the workflow if the diff crosses a threshold.

      - name: Fail on large cost increases
        run: |
          DIFF=$(jq -r '.diffTotalMonthlyCost' /tmp/infracost.json)
          THRESHOLD=500
          if (( $(echo "$DIFF > $THRESHOLD" | bc -l) )); then
            echo "::error::PR adds \$$DIFF/month (threshold: \$$THRESHOLD)"
            echo "Request review from #finops in Slack before merging."
            exit 1
          fi

Pair this with branch protection requiring the workflow to pass, and any PR over $500/month is blocked until a designated reviewer overrides it (typically by adding a label that the workflow checks for and skips on).

OPA / Rego for Richer Rules

For more nuanced rules (e.g. "block PRs that create a NAT Gateway in more than two AZs", "warn if any new RDS instance is larger than db.r6g.xlarge", "require approval if the change adds Spot capacity over 50% of the cluster"), use Open Policy Agent against the Infracost JSON output:

# cost-policy.rego
package infracost

deny[msg] {
  resource := input.projects[_].breakdown.resources[_]
  resource.resourceType == "aws_nat_gateway"
  count_nat_gateways > 2
  msg := "More than 2 NAT Gateways. Use VPC endpoints or a single NAT with TGW"
}

warn[msg] {
  resource := input.projects[_].breakdown.resources[_]
  resource.resourceType == "aws_db_instance"
  resource.monthlyCost > 800
  msg := sprintf("RDS instance %s costs $%.0f/month, confirm sizing",
                 [resource.name, resource.monthlyCost])
}

Run opa eval --data cost-policy.rego --input /tmp/infracost.json in the workflow and fail on any deny result. The same Rego rules can live alongside your security policies: one engine, one policy directory, two domains.

Infracost Cloud: The Dashboard Layer

The free CLI is enough for most use cases. Infracost Cloud (paid tier) adds organisation-wide visibility on top: every PR's cost diff is pushed to a dashboard so platform teams can see trends across repos, identify the cost-heavy projects, and review policy violations across the fleet rather than per-PR.

It's useful at scale (when you have 40 Terraform repos and want to know which teams are driving cost growth), but for a single repo, the GitHub PR comment is usually all you need. Start with the free CLI; reach for the Cloud tier when you outgrow the per-repo view.

A Cooked War Story

The PR that wasn't: A platform team I worked with rolled out Infracost on a Friday afternoon, the "low risk" deploy window. On Monday morning, the first PR of the week was a junior engineer adding a "small" Aurora cluster for a new analytics service. The PR comment showed +$2,340/month. The engineer had picked db.r6g.4xlarge from a copy-pasted module without realising the parent module's default was eight-core. Code review would have caught it eventually, but only when someone with Aurora pricing in their head reviewed it. Infracost caught it in 90 seconds. The engineer dropped the instance size to db.r6g.large, the cost dropped to $290/month, and the PR merged the same day.

The pattern that played out wasn't dramatic. No $50k disaster averted, no executive escalation. It was just a small, ordinary mistake getting caught at the right moment. Multiply that by every PR over a quarter and the compounding effect is significant. Cost discipline isn't built by catching the one catastrophic change; it's built by surfacing the dozens of mid-sized ones that would otherwise slip through.

Where It Falls Short

Infracost is excellent at what it does, but it isn't a complete FinOps platform. The honest limitations:

  • It prices what Terraform creates, not what's running. Resources provisioned outside Terraform (Console clickops, CloudFormation, Pulumi) are invisible. If 30% of your AWS spend is unmanaged infrastructure, Infracost only sees the other 70%.
  • Usage estimates depend on the usage file. No infracost-usage.yml means S3 storage, Lambda invocations, NAT Gateway transfer, and CloudFront data are reported as "depends on usage" with no dollar figure. Garbage in, garbage out, and "no input" is the most common form of garbage.
  • It doesn't model commitments. Savings Plans, Reserved Instances, and EDP discounts aren't reflected in the estimate. Infracost shows on-demand prices, which is the worst case. Your actual bill is usually lower (sometimes by 30–60%), but the diff direction is still accurate.
  • It can't see runtime dynamics. An autoscaling group sized 1–100 is priced at its minimum unless you set the usage file to a realistic average. Karpenter NodePools are priced at zero until pods actually request capacity. Spot pricing is approximated from on-demand.
  • Module-heavy plans need care. Deeply nested modules sometimes confuse the resource matcher. Run infracost breakdown --show-skipped periodically to see which resources Infracost couldn't price; it's usually obvious which ones matter.

None of this disqualifies it. Treat the number as directional, not exact. The point isn't to predict your bill to the dollar; it's to surface order-of-magnitude mistakes before they ship.

Key Takeaways

  1. Cost is a shift-left problem. The information needed to prevent surprises exists at PR time. Infracost is the glue between Terraform plans and AWS pricing.
  2. Two commands cover 90% of usage. infracost breakdown for total cost, infracost diff for change. Everything else builds on these.
  3. Write a usage file. Without infracost-usage.yml, variable costs (Lambda, S3 requests, NAT data, DynamoDB units) are invisible. With it, you see what actually matters.
  4. GitHub Actions integration is the productivity multiplier. A sticky PR comment with --behavior=update puts cost where reviewers already look.
  5. Comments nudge, policies block. Use threshold checks for blunt guardrails, Rego for nuanced rules. Both run on the same JSON output.
  6. It prices Terraform, not your bill. Unmanaged resources, commitments, and runtime dynamics aren't modelled. Treat the number as directional: accurate enough to catch architecture mistakes, not accurate enough to forecast invoices.
  7. Start with the free CLI. Add Infracost Cloud only when you need organisation-wide visibility. For a single repo, the PR comment is enough.
