Five AWS MCP Servers Worth Wiring Up, and the IAM Boundary That Makes Them Safe

Richie Richard Rajkumar · September 2026 · 19 min read

Most of the time an infrastructure engineer loses to AWS is not spent solving the problem. It is spent on retrieval. You know exactly what you want to know, which staging instances have been idle for a fortnight, and the next ten minutes go on remembering the shape of the --filters argument for describe-instances, then pivoting to CloudWatch because the CLI does not return utilisation, then reconciling two lists by eye. The thinking took fifteen seconds. The retrieval took a quarter of an hour.

MCP servers collapse that gap. An agent holding AWS credentials can construct the call, run it, read the result, and issue the follow-up call without you context-switching between four consoles. The catch is that searching for "AWS MCP server" returns a field of abandoned forks, half-written wrappers, and blog posts describing packages that no longer install. So I limited this to the servers that live in awslabs/mcp, are officially maintained by AWS Labs, and are still being shipped in 2026. I checked each one against its current documentation while writing this, and the package names and tool lists below are what the docs say today, not what they said last year.

There are two things I want to spend more time on than the usual list does. The first is the IAM work that comes before any of this, because the interesting failure mode is not a broken server, it is a read-only role that quietly turns out to include s3:GetObject. The second is AWS's own managed MCP server, which went generally available in May 2026 and changes the calculus on whether you should be running these processes locally at all.

IAM First, Servers Second

Every server here works the same way: it takes the AWS credentials you hand it and makes API calls on your behalf. There is no sandbox, no per-tool permission model, and no server-side restriction that is meaningfully independent of IAM. The AWS API MCP Server documentation is admirably direct about this: "IAM permissions remain the primary and most reliable security control." That sentence is the whole security architecture. Everything else is a convenience flag.

So before installing anything, create a dedicated role. Not your engineer role. Not an admin role with a mental note to be careful. A role that exists only to be assumed by an agent, so that when you read CloudTrail six weeks from now you can tell agent activity from human activity by the principal alone.

# The role an agent assumes. Short sessions, MFA on the human upstream,
# and a boundary that survives someone later attaching a wider policy.
resource "aws_iam_role" "mcp_readonly" {
  name                 = "mcp-agent-readonly"
  max_session_duration = 3600
  permissions_boundary = aws_iam_policy.mcp_boundary.arn

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Action    = ["sts:AssumeRole", "sts:TagSession"]
      Principal = { AWS = "arn:aws:iam::${var.account_id}:root" }
      Condition = {
        StringEquals = { "aws:PrincipalTag/MCPAgent" = "true" }
        Bool         = { "aws:MultiFactorAuthPresent" = "true" }
      }
    }]
  })
}

resource "aws_iam_role_policy_attachment" "mcp_readonly" {
  role       = aws_iam_role.mcp_readonly.name
  policy_arn = "arn:aws:iam::aws:policy/ReadOnlyAccess"
}

ReadOnlyAccess reads your data, not just your metadata

This is the part that gets skipped. ReadOnlyAccess is not a resource-inventory policy. It grants read across the data plane too, which includes s3:GetObject, and depending on the current revision of the policy, secret and parameter reads as well. An agent with that role attached is one confused tool call away from pulling the contents of an object into a conversation transcript that then gets stored by whatever client you are using.

A permissions boundary fixes this properly, because unlike a policy someone can detach, a boundary caps the role's effective permissions no matter what gets attached to it later.

resource "aws_iam_policy" "mcp_boundary" {
  name = "mcp-agent-boundary"
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      { Effect = "Allow", Action = "*", Resource = "*" },
      {
        # Metadata yes, contents no.
        Effect = "Deny"
        Action = [
          "s3:GetObject",
          "s3:GetObjectVersion",
          "secretsmanager:GetSecretValue",
          "ssm:GetParameter",
          "ssm:GetParameters",
          "ssm:GetParametersByPath",
          "kms:Decrypt",
          "dynamodb:GetItem",
          "dynamodb:Scan",
          "dynamodb:Query",
          "lambda:GetFunction",
          "iam:*",
          "sts:AssumeRole"
        ]
        Resource = "*"
      }
    ]
  })
}

Two notes on that deny list. lambda:GetFunction returns a presigned URL to the deployment package, so it is a code-exfiltration path dressed as a metadata call. And iam:* is denied here deliberately, which means this role cannot be used for the IAM server. That is the point: an access-review tool and a general investigation tool should not share a principal. Give the IAM server its own role scoped to iam:List*, iam:Get*, iam:Simulate*, and nothing else.

The Cost Explorer gap

ReadOnlyAccess also does not cover Cost Explorer, Compute Optimizer, or Cost Optimization Hub, so the billing server will fail with access-denied errors that look like a broken install. Attach these explicitly:

resource "aws_iam_policy" "mcp_cost_read" {
  name = "mcp-agent-cost-read"
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Action = [
        "ce:Get*", "ce:Describe*", "ce:List*",
        "compute-optimizer:Get*", "compute-optimizer:Describe*",
        "cost-optimization-hub:Get*", "cost-optimization-hub:List*",
        "budgets:Describe*", "budgets:View*",
        "savingsplans:Describe*", "savingsplans:List*"
      ]
      Resource = "*"
    }]
  })
}
Turn CloudTrail on for this role before the first query, not after the first surprise. The single most useful artefact from running agents against AWS is a queryable log of every call one made under your credentials. You are accountable for what runs under that role regardless of whether a person or a model composed the request, and the only way that accountability is real rather than rhetorical is if you can reconstruct the sequence afterwards.

The Five Servers

All five install identically. They are Python packages published to PyPI, run over stdio, and launched with uvx so you are not managing virtualenvs. SSE transport was removed from these servers in 2025; stdio is the only supported transport. Any client that speaks MCP works, including Claude Code, Claude Desktop, Amazon Q Developer CLI, Cursor, and Kiro.

1 · AWS API MCP Server

Package: awslabs.aws-api-mcp-server

The broadest of the five, and the right default. It exposes the AWS CLI itself as a natural-language interface, which means its surface area is effectively every service the CLI covers. Three tools do the work: call_aws executes a validated CLI command, suggest_aws_commands proposes commands from a description, and get_execution_plan (experimental) sketches multi-step approaches.

The validation step matters more than it sounds. The server checks the command is syntactically valid against the CLI's own model before executing, so the common agent failure of inventing a plausible-looking flag that does not exist gets caught locally rather than producing a confusing API error.

// ~/.aws-mcp/config.json (or your client's MCP config)
{
  "mcpServers": {
    "aws-api": {
      "command": "uvx",
      "args": ["awslabs.aws-api-mcp-server@latest"],
      "env": {
        "AWS_API_MCP_PROFILE_NAME": "mcp-agent-readonly",
        "AWS_REGION": "eu-central-1",
        "READ_OPERATIONS_ONLY": "true",
        "REQUIRE_MUTATION_CONSENT": "true",
        "FASTMCP_LOG_LEVEL": "ERROR"
      }
    }
  }
}

Set both READ_OPERATIONS_ONLY and REQUIRE_MUTATION_CONSENT. Treat them as defence in depth on top of the IAM role, never as a substitute: they are process-local flags that an operator can flip in a config file, whereas the role is enforced by AWS.

// prompts worth trying
  • List every EC2 instance in eu-central-1 whose average CPU over the last 14 days is under 5%. Show instance type, launch time, and the Name tag, sorted by instance type.The classic idle hunt. Spans describe-instances and CloudWatch in one pass, which is the bit that normally costs you ten minutes.
  • Which security groups allow 0.0.0.0/0 on a port other than 80 or 443? For each one, tell me whether it is actually attached to a running network interface.The second sentence is what makes this useful. Most raw findings are attached to nothing and are noise.
  • Find every Lambda function with no invocations in the last 30 days, and for each, say whether it still has an event source mapping or trigger wired up.Distinguishes dead code from code that is idle but still reachable. Only the first group is safe to delete.
  • Compare the RDS parameter groups used by prod and staging and list only the parameters that differ.Drift detection between environments. Painful in the console, trivial as a diff.
  • List unattached EBS volumes and unassociated Elastic IPs, with size, creation date, and the ID of whatever they were last attached to.Zombie cleanup with enough context to be confident about deleting.
  • Show me every S3 bucket where Block Public Access is not fully enabled, and print the bucket policy for each.Give it the raw policy rather than asking it to judge. You decide, it retrieves.

2 · CloudWatch MCP Server

Package: awslabs.cloudwatch-mcp-server

This is the one that changed my day-to-day most. It is not a thin wrapper over the CloudWatch API; it exposes sixteen task-oriented tools grouped into metrics, alarms, logs, and PromQL. The distinction matters because the raw CloudWatch API is one of the least pleasant surfaces in AWS to drive by hand, and Logs Insights in particular has a query language that most engineers relearn from scratch every time they need it.

  • Alarms: get_active_alarms, get_alarm_history. Alarm-based troubleshooting is a first-class flow: from a firing alarm the server can pull the related metrics, the relevant log groups, and the historical pattern of that alarm.
  • Metrics: get_metric_data, analyze_metric, get_metric_metadata, get_recommended_metric_alarms. That last one is quietly useful for greenfield services where nobody has decided what to alarm on yet.
  • Logs: describe_log_groups, analyze_log_group, execute_log_insights_query, execute_cwl_insights_batch, plus polling and cancellation tools for long-running queries.
  • PromQL: five tools for instant and range queries, label and series discovery. If you are running Managed Prometheus alongside CloudWatch, this removes the last reason to keep a separate query console open.

It also ships investigation skills built on AgentCore, which encode common troubleshooting sequences so the agent follows a structured path rather than improvising a different route through the same data every time.

Watch the query cost on Logs Insights. An agent that decides to scan a month of logs across every log group to answer a vague question will do exactly that, and CloudWatch bills Logs Insights on data scanned. Scope your prompts to a log group and a time window, or you will find the retrieval convenience showing up on the bill as its own line item.
// prompts worth trying
  • The payments-api-5xx alarm is firing. Pull its history for the last week, the metrics it watches, and any error patterns in /aws/ecs/payments-api during the current breach.The full alarm-to-metric-to-log walk in one prompt. This is the flow the server was built for.
  • Find the top 20 error messages by count in /aws/eks/prod/application over the last 6 hours, grouped by the pod that emitted them.A Logs Insights query nobody remembers how to write. Note the explicit log group and window.
  • Which alarms are in ALARM or INSUFFICIENT_DATA right now, and which of those have changed state more than five times in the last 24 hours?INSUFFICIENT_DATA is where dead alarms hide. The flapping filter finds the ones nobody trusts any more.
  • This service went live last week and has no alarms. Look at its metrics for the last two weeks and recommend alarm thresholds with reasoning.Exercises get_recommended_metric_alarms. Treat the output as a first draft, not a config.
  • Run a PromQL range query for container_memory_working_set_bytes on the checkout deployment over 7 days and tell me how close it gets to its limit.Only useful if you run Managed Prometheus, and then it removes the last reason to keep a second console open.
  • Compare the error rate and p99 latency of the api-gateway service this week against the same week last month.Period-over-period comparison, which the CloudWatch console makes needlessly awkward.

3 · AWS Billing and Cost Management MCP Server

Package: awslabs.billing-cost-management-mcp-server

This is the current cost server. If you find a guide pointing at cost-explorer-mcp-server, that package is deprecated in the repository in favour of this broader one. The replacement is not a rename: it spans Cost Explorer, Budgets, Cost Anomaly Detection, Compute Optimizer, Cost Optimization Hub, Savings Plans, Pricing and the Pricing Calculator, S3 Storage Lens, Billing Conductor, cost allocation tags, cost categories, invoicing, credits, and Free Tier usage.

The practical consequence of that breadth is that one question can cross sources that used to require three separate consoles. "Our EC2 spend jumped 22% in the last fortnight, what changed and is there a savings recommendation" pulls from Cost Explorer for the trend, Anomaly Detection for the flag, and Cost Optimization Hub for the recommendation, in one turn.

{
  "mcpServers": {
    "aws-billing": {
      "command": "uvx",
      "args": ["awslabs.billing-cost-management-mcp-server@latest"],
      "env": {
        "AWS_PROFILE": "mcp-agent-readonly",
        "AWS_REGION": "us-east-1",
        "FASTMCP_LOG_LEVEL": "ERROR"
      }
    }
  }
}

Note the region. Cost Explorer is a us-east-1 global endpoint regardless of where your workloads run, and pointing this server at your workload region is the most common reason it appears to return nothing.

Two costs to be aware of. Cost Explorer's API is a paid API, billed per request at AWS's published rate of roughly a cent per call, which is trivial for a human clicking through the console and non-trivial for an agent that decides to iterate across twelve dimensions to be thorough. And Storage Lens functionality runs through Athena, so it needs a manifest location and an output bucket configured via STORAGE_LENS_MANIFEST_LOCATION and STORAGE_LENS_OUTPUT_LOCATION, and it bills like Athena.

// prompts worth trying
  • Compare this month's spend to last month by service, and show only services that moved by more than 10% or $200.The threshold is doing real work here. Without it you get all forty services and have to rank them yourself.
  • Any cost anomalies detected in the last 30 days? For each, give the service, the dollar impact, and the date it started.The start date is what makes an anomaly actionable, because it tells CloudTrail where to look next.
  • List our Cost Optimization Hub recommendations sorted by estimated monthly saving, and give me the total if we implemented all of them.One call replaces a tour of three separate consoles.
  • Show Compute Optimizer rightsizing recommendations for instances tagged env=production, and flag any that would require a different instance family.The family flag matters: a cross-family move is a compatibility question, not just a size change.
  • What is our Savings Plans coverage and utilisation right now, how much on-demand spend is uncovered, and what would a 1-year no-upfront Compute plan at that level cost?Coverage and utilisation together. High utilisation with low coverage means buy more, the reverse means you over-committed.
  • Break down our S3 costs by bucket and storage class, and identify buckets where most objects are under 128 KB.The small-object check that decides whether Intelligent-Tiering will help or cost you money.

4 · AWS CloudTrail MCP Server

Package: awslabs.cloudtrail-mcp-server

This answers "who did this, and when." lookup_events covers the last 90 days of management events that CloudTrail retains by default, filterable by username, event name, resource, and time. If you have CloudTrail Lake enabled, lake_query runs Trino-compatible SQL against event data stores, which extends the reach to as much history as you have chosen to retain, up to ten years.

That second capability is the one worth setting up. Ninety days of point lookups is useful during an incident. SQL over years of history is what lets you answer compliance and forensic questions that were previously a multi-day exercise in CSV exports.

# IAM actions this server needs (its own read role, not the general one)
cloudtrail:LookupEvents
cloudtrail:ListEventDataStores
cloudtrail:GetEventDataStore
cloudtrail:StartQuery
cloudtrail:DescribeQuery
cloudtrail:GetQueryResults

The remaining tools, list_event_data_stores, get_query_status, and get_query_results, exist because Lake queries are asynchronous. The agent starts a query, polls for completion, and pages the results, which is exactly the kind of three-step mechanical sequence that is tedious by hand and invisible when a tool does it.

// prompts worth trying
  • What IAM changes happened in the last 24 hours and who made them? Exclude anything from the terraform-apply role.The exclusion is the whole trick. Filtering out your own automation leaves only what needs explaining.
  • The bucket assets-prod became publicly readable at some point. Find the API call that changed it, then show everything that principal did in the hour either side.Point-in-time plus blast radius. The second half is what a console investigation usually skips.
  • Show every ConsoleLogin event in the last 30 days where MFA was not used, with the source IP and whether it succeeded.Straight out of most audit checklists, and about four clicks per result by hand.
  • Has the root account made any API call in the last 90 days? If so, what, when, and from where.Should return nothing. If it returns something, that is your afternoon.
  • Using CloudTrail Lake, list the top 25 principals by write API call count over the last 12 months, and for each show the first and last time they were active.Needs Lake enabled. The last-active column is how you find credentials nobody has used since a departure.
  • Using CloudTrail Lake, find every AssumeRole call into the prod-admin role over the last year, grouped by the originating principal.Twelve months of privileged-access history as one SQL query rather than a CSV export project.

5 · AWS IAM MCP Server

Package: awslabs.iam-mcp-server

Built for access hygiene. It enumerates users, roles, groups, and both managed and inline policies, and its most valuable tool is iam:SimulatePrincipalPolicy exposed as policy simulation: you can ask whether a given principal would be allowed a given action before you change anything. That converts "I think this policy is too broad" from an argument into a test.

It can also create and delete users, roles, and access keys. Do not let it. Run it with the --readonly flag, which disables every mutating tool while leaving list and get intact.

{
  "mcpServers": {
    "aws-iam": {
      "command": "uvx",
      "args": ["awslabs.iam-mcp-server@latest", "--readonly"],
      "env": {
        "AWS_PROFILE": "mcp-agent-iam-audit",
        "FASTMCP_LOG_LEVEL": "ERROR"
      }
    }
  }
}

A separate profile, deliberately. This is the one server on the list whose write capabilities could compromise the security of everything else on the list, including its own audit trail. It gets an IAM-scoped read role and nothing more.

// prompts worth trying
  • Which IAM users have console access but no MFA device? Include when their password was last used.The last-used date splits genuine risk from dormant accounts you should be deleting anyway.
  • Find every customer-managed policy with a wildcard in both Action and Resource, and list which users, roles, and groups it is attached to.An unattached over-broad policy is a cleanup task. An attached one is a finding.
  • Simulate whether the role eks-node-prod is allowed to call s3:DeleteObject on arn:aws:s3:::assets-prod/*, and tell me which policy statement decides the outcome.Policy simulation, the best tool on this server. Turns an argument about a policy into a test with an answer.
  • List all access keys older than 90 days with their last-used date and which service they were last used against.The service column tells you what will break before you rotate.
  • Which roles in this account can be assumed by a principal outside the account, and what does each trust policy actually permit?Cross-account trust is where the genuinely surprising findings live.
  • List every role with an AdministratorAccess attachment, and for each show whether it has a permissions boundary.Admin plus no boundary is the combination worth a same-day conversation.

The Sixth Option: AWS's Managed MCP Server

The five above are local processes holding your credentials. In May 2026 AWS made a remote, fully managed alternative generally available, and most lists written before then do not mention it. It is worth understanding before you commit to a local-only setup.

# Connect through the proxy; auth uses SigV4 with your existing credentials
uvx mcp-proxy-for-aws@latest https://aws-mcp.us-east-1.api.aws/mcp

The managed server covers a very wide API surface, ships with current AWS documentation and curated skills, provides sandboxed Python execution, and authenticates through your own IAM identity rather than a long-lived credential sitting in a config file. Calls are validated server-side and logged to CloudTrail as a matter of course.

DimensionLocal awslabs serversManaged AWS MCP Server
Credential exposure Profile readable by the local process SigV4 under your IAM identity, nothing stored
Breadth Five focused servers, task-shaped tools Very wide API coverage plus live docs
Depth per domain Purpose-built (PromQL, Lake SQL, policy sim) Generalist, thinner on specialised flows
Version control You pin the package AWS ships changes when AWS ships them
Air-gapped or restricted networks Works offline against VPC endpoints Requires reaching the AWS endpoint
Operational burden Every engineer maintains local config Nothing to maintain

My read: the managed server is the better starting point for most teams, precisely because it removes the credentials-in-a-config-file problem that is the weakest link in every local setup. Add the specific local servers on top where their depth genuinely matters, which in practice means CloudWatch if you live in Logs Insights and PromQL, CloudTrail if you have Lake enabled, and the billing server if cost work is a recurring part of the job. That is a hybrid, and hybrids are unfashionable, but it puts the credential handling where AWS can enforce it and keeps the specialised tools where you need them.

// prompts that show what the managed server adds
  • Check the current EKS documentation and tell me whether Auto Mode supports a custom CNI configuration yet. Quote the relevant section.The differentiator: it reads live docs rather than answering from a training cut-off. Asking for the quote is how you check it actually looked.
  • Using current pricing, what would 40 m7g.xlarge instances cost per month in eu-central-1 on demand versus a 1-year no-upfront Compute Savings Plan?Pricing maths in the sandboxed Python runtime, against current rates rather than remembered ones.
  • What is the recommended way to give a pod in EKS access to an S3 bucket in another account in 2026? Tell me what has changed since IRSA.The what-has-changed framing is the point. This is the question a stale answer gets wrong most often.

Where the Value Actually Shows Up

Taken one at a time, none of these servers gives you a capability you did not have. The CloudWatch server does not know anything a Logs Insights query would not have told you. It removes the friction of writing the query, which is worth something, but it is not new power.

The step change is composition. Multiple servers in one conversation let an agent join data that no single console view joins, and that is where questions get answered that previously took a person forty minutes of tab-switching and note-taking to assemble.

Security posture review

  1. aws-api: security groups with unrestricted ingress, buckets with public access configurations, unencrypted volumes.
  2. iam: users with console access and no MFA, roles with wildcard resources, access keys older than 90 days.
  3. cloudtrail: any root-account API activity in the last 30 days, and any iam:* calls made outside the change window.
  4. Synthesis: one prioritised list, ordered by exploitability rather than by which tool found it.

That last point is the whole benefit. Three separate scans produce three separate lists that a human then has to rank against each other. One conversation produces a ranking, because the agent knows that a public bucket matters more when an IAM role with wildcard access can reach it.

Incident root cause

You:
The payments-api started returning 503s at 14:20 UTC today and recovered at 14:52. Nothing was deployed. Find out what changed.
Agent:
I traced this across CloudWatch and CloudTrail.

What broke (CloudWatch): payments-api target group healthy host count dropped from 6 to 0 at 14:19:48. Application logs show connection timeouts to payments-db.cluster-xxxx.eu-central-1.rds.amazonaws.com on port 5432, not application errors. The service itself was healthy; it could not reach its database.

What changed (CloudTrail): a single RevokeSecurityGroupIngress call at 14:19:31, twelve seconds before the drop. Security group sg-0a41... (the RDS security group), removing the rule that allowed 5432 from sg-0b77... (the EKS node group). Principal: arn:aws:sts::...:assumed-role/terraform-apply/GitHubActions-8841.

Why (aws-api plus CloudTrail): the reverse call AuthorizeSecurityGroupIngress appears at 14:51:40 from the same principal. This is a Terraform apply that recreated the rule rather than leaving it in place, which suggests the rule was moved between resources in the configuration. The 32-minute gap is the duration of the apply.

Conclusion: not an outage, a self-inflicted revoke-then-recreate during a Terraform run. The fix is a create_before_destroy lifecycle block on that rule, and the reason nobody noticed a deployment is that the change was to infrastructure, not to the service.

Every fact in that answer was available to you before. CloudTrail had the event, CloudWatch had the metric, the security group state was one CLI call away. What you did not have was the join, and the join is the part that took forty minutes.

Cost anomaly triage

  1. billing: which service and usage type drove the increase, and when it started.
  2. cloudtrail: what was created or modified in that service around that timestamp, and by whom.
  3. aws-api: whether those resources are still running and whether anything is attached to them.

This is the loop that turns a monthly billing surprise into a same-day operational signal, which is the actual goal of cost work. I have written separately about the ordering of AWS cost levers and about catching cost changes at PR time; the billing server is the third leg of that, covering the spend that has already happened.

// composed prompts, two or more servers in one turn
  • Our EC2 spend rose 22% starting around the 14th. Find what drove it in Cost Explorer, then check CloudTrail for what was created in that service around that date and by whom, then tell me whether those resources are still running.billing + cloudtrail + aws-api. The three-console cost investigation as one sentence.
  • Run a security posture review: unrestricted security groups and public buckets, users without MFA and roles with wildcard resources, and any root activity in the last 30 days. Give me one list ordered by exploitability, not by which check found it.aws-api + iam + cloudtrail. The ordering instruction is what you are actually buying here.
  • The checkout service degraded between 09:10 and 09:40 UTC. Correlate its CloudWatch metrics and logs with every CloudTrail event touching its infrastructure in that window, and name the change most likely responsible.cloudwatch + cloudtrail. Ask it to name a cause and it commits to something you can check, rather than handing you two timelines.
  • For the top five namespaces by cost this month, check whether each has had a deployment in the last 30 days and whether its alarms have fired. Flag anything expensive, undeployed, and quiet.billing + aws-api + cloudwatch. That combination is the signature of a service nobody owns any more.
Three habits that make these prompts work better. Name the region, log group, and time window explicitly, because an unscoped question invites the agent to scan everything and both CloudWatch and Cost Explorer bill for that. Ask for the evidence alongside the conclusion, a policy statement, an event ID, a quoted doc section, so you can check the answer without redoing the work. And when a finding is only interesting in context, say so in the prompt: "tell me which of these are actually attached to something" turns forty raw results into the four that matter.

The Problem Nobody Puts in the Feature List

The AWS API MCP Server documentation states plainly that the server offers no protection against prompt injection, is designed for single-user use, and does not sandbox filesystem access. I would rather quote that than paraphrase it, because it is unusually honest for vendor documentation and it defines the threat model precisely.

What it means in practice: an agent that reads untrusted text and also holds AWS credentials is a confused deputy waiting to happen. The text does not have to arrive through a dramatic channel. A resource tag, an EC2 instance name, an S3 object key, a CloudWatch log line containing a user-submitted string, a CloudTrail userAgent field. All of these are attacker-influenceable in some architectures, and all of them flow into the agent's context as ordinary tool output.

The mitigations are unglamorous and they all live below the agent:

  • Read-only at the IAM layer, with data reads denied. Injection that can only enumerate resources is a nuisance. Injection that can read secrets or delete infrastructure is an incident. This is what the permissions boundary above is for.
  • Never point a credentialed agent at a bucket or log group carrying user-generated content. If you need to analyse that data, do it in a session with no write capability and no access to anything else.
  • Separate roles per server, always. A compromise of the general investigation context should not reach IAM.
  • Short session durations. One hour, so a leaked session credential has a short half-life.
  • Read the CloudTrail log. Not as an afterthought. A weekly review of what the agent role actually called is the only control that catches a problem you did not anticipate.
The honest framing: connecting an agent to your AWS account is onboarding a very fast contractor with no judgement about consequences and a tendency to be helpful. You would scope that person's access narrowly, log what they did, and review it. Do the same here, and the residual risk is manageable. Skip it, and you have handed ReadOnlyAccess to a process that reads text from the internet.

A Staged Rollout

Adding all five at once produces overlapping tool calls and a lot of noise, because the agent has no basis for choosing between three servers that could plausibly answer the same question. Worse, you never build the intuition for which one is right, so you cannot tell a bad answer from a good one. Stage it.

WeekAddGoalDo not yet
0 The IAM role and boundary. No servers. CloudTrail logging confirmed working on the role Install anything
1 aws-api, read-only Ask real questions daily. Learn where it guesses. Grant any write
2 cloudwatch Use it on a real incident. Compare to your manual path. Broad unscoped log queries
3 cloudtrail First composed question: metric drop plus the change that caused it Lake, until you have checked retention
4 billing Monthly cost review as a conversation, not a console tour Unbounded dimension sweeps
5 iam, separate role, --readonly Full posture review composing all four others Ever remove --readonly

Five weeks feels slow and it is not. The constraint is not installation time, it is the time it takes you to develop a reliable sense of when a given server's answer should be trusted and when it should be checked. Compressing that produces a team that either distrusts the tooling entirely or, much worse, trusts it uniformly.

What I Would Not Do

Grant write access on day one

The pitch for write access is that the agent could remediate what it finds. The problem is that remediation is where being confidently wrong becomes expensive, and read-only investigation is where these servers deliver almost all their value anyway. If you eventually want mutation, route it through the path you already have for changes: the agent proposes a Terraform diff, a human reviews it, CI applies it. That keeps the audit trail and the review gate you have already built rather than opening a second, unreviewed path into production.

Share one role across all servers

It is the obvious convenience and it defeats the main control. A shared role means CloudTrail cannot tell you which tool made a call, and a problem in any one context reaches everything. One role per server, named after the server.

Run these against production from a laptop

Local stdio servers mean production credentials on developer machines, which is the thing every credential-hygiene programme has spent a decade trying to eliminate. Use the managed server, or run the local servers on a bastion or in a container with the role attached rather than a profile on disk. The convenience of local install is real, and it is not worth reintroducing static credentials to get it.

Trust a package name from a blog post, including this one

The deprecation of cost-explorer-mcp-server is a good illustration. It was the right answer, then it was not, and a lot of guides still recommend it. Check awslabs.github.io/mcp before you install. The list moves.

Key Takeaways

  1. IAM is the security model, not a detail before it. AWS's own docs say IAM permissions are the primary and most reliable control. The READ_OPERATIONS_ONLY flag is defence in depth on top of that, never instead of it.
  2. ReadOnlyAccess reads data, not just metadata. It covers s3:GetObject and, depending on the policy revision, secret and parameter reads. Add a permissions boundary that denies data-plane reads and lambda:GetFunction, which returns a presigned link to your code.
  3. Five servers, five roles. The IAM server in particular gets its own principal, scoped to IAM reads and policy simulation, and always runs with --readonly.
  4. Start with the AWS API server. Broadest surface, no extra IAM, no per-query cost. It is the right default for general investigation.
  5. The CloudWatch server is the biggest daily quality-of-life gain. Sixteen task-shaped tools over metrics, alarms, Logs Insights, and PromQL, which is the surface engineers most dislike driving by hand.
  6. Use the billing server, not the deprecated Cost Explorer one, point it at us-east-1, attach ce:* read permissions explicitly, and remember Cost Explorer bills roughly a cent per API call.
  7. Enable CloudTrail Lake if you can. It turns the CloudTrail server from 90 days of point lookups into SQL over years of history, which is a different class of tool.
  8. Consider the managed AWS MCP Server first. GA since May 2026, it removes credentials from local config entirely. Add local servers on top only where their depth earns it.
  9. There is no prompt-injection protection. Documented, not speculative. Never combine credentialed agent sessions with untrusted text, and remember that tags, object keys, and log lines are untrusted text.
  10. The gain is composition, not any single server. CloudTrail says when, IAM says who, CloudWatch says what broke, billing says what it cost. Answering those together in one pass is the actual product.
  11. Scope every prompt. Name the region, log group, and time window, and ask for the evidence alongside the conclusion. Unscoped questions are how a retrieval convenience turns into a CloudWatch and Cost Explorer line item.
  12. Stage the rollout over weeks. One role, one server, real questions for a week. The bottleneck is calibrating your own trust in the answers, and that cannot be parallelised.
