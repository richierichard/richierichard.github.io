EKS Auto Mode: Letting AWS Run the Data Plane (and What It Costs You)

Richie Richard Rajkumar · June 2026 · 18 min read

EKS gives you three ways to run the data plane. Self-managed node groups put everything in your hands, the AMI, the Auto Scaling Group, the bootstrap scripts, the kubelet flags. EKS managed node groups (MNGs) hand AWS the AMI and the rolling upgrade lifecycle while you keep control over scaling and addons. EKS Auto Mode, generally available since December 2024, goes further: AWS runs the nodes, runs Karpenter, runs the load balancer controller, runs the CSI and CNI drivers, and rotates your nodes every 21 days for security patching. You bring workloads and a NodePool. AWS brings the rest.

That sounds great, until you read the pricing page. Auto Mode adds an EC2 management fee, roughly 12% on top of the underlying instance cost in eu-central-1. For a 5-node platform cluster like mine, that is around 25 EUR a month extra. For a 50-node production fleet running Spot at scale, the same 12% becomes meaningful FinOps territory. This article is a decision and migration guide: what Auto Mode actually does, how it differs from self-managed and MNG setups, what the real numbers look like in eu-central-1, and how to migrate to it from either a managed node group cluster or from a self-hosted Karpenter cluster.

What EKS Auto Mode Actually Is

The marketing line is "EKS, fully managed". The technical reality is more useful: Auto Mode is a bundle of AWS-managed components that sit on top of a normal EKS cluster and remove your responsibility for the data plane scaffolding most teams build by hand.

When you enable Auto Mode on a cluster, AWS turns on the following as a single managed unit:

  • Managed compute, a built-in Karpenter implementation that AWS operates. You still define NodePool and NodeClass CRDs (the latter is the Auto Mode flavour, eks.amazonaws.com/NodeClass, not the Karpenter community EC2NodeClass). AWS handles the controller upgrades, the IAM wiring, the SQS interruption queue, and the Karpenter version.
  • Bottlerocket-only nodes, immutable, minimal, container-optimised. There is no AL2023 or AL2 option in Auto Mode. SSH and SSM access are disabled. Nodes are treated as cattle that you cannot pet.
  • Automatic node refresh, every node is replaced at most every 21 days. AWS pulls a freshly patched Bottlerocket AMI, drains the old node, and provisions a new one. No more "schedule the AMI rotation" tickets.
  • Managed networking, VPC CNI, kube-proxy, CoreDNS, plus a built-in AWS Load Balancer Controller exposed through a new IngressClass (eks-auto-alb) and LoadBalancerClass (eks.amazonaws.com/nlb).
  • Managed storage, the EBS CSI driver is built in, with a default gp3 storage class managed by Auto Mode. The volumes are tagged and lifecycle-managed by AWS as part of the cluster.
  • Managed Pod Identity and Node Monitoring agents, no separate addon installs.

What stays yours: the EKS control plane configuration (same as before), the VPC and subnets, the IAM roles for your workloads, your applications, and the NodePool CRDs that describe what kinds of nodes Auto Mode is allowed to provision. Everything between your pods and the EC2 API is the AWS managed surface.

The mental model: Auto Mode is EKS with the "boring but necessary" parts pre-wired. It is not Fargate, you still get real EC2 nodes, you still pay per instance, you still see them in the EC2 console. The difference is that you no longer install or upgrade the controllers that make those nodes useful.

The Three Modes Compared

Before deciding, it helps to see the three options side by side. The same workload runs on the same Kubernetes API on all three, but the operational and pricing surface looks different.

Where the line moves

The pattern is consistent: each step right hands AWS another job and shrinks the surface you have to maintain, in exchange for less flexibility on the underlying primitives and, in Auto Mode's case, a per-instance fee. Self-managed gives you GovCloud-grade control, MNGs are the comfortable middle ground that almost every EKS cluster runs today, and Auto Mode is the "I do not want to think about the data plane" option.

Workload Isolation: Custom NodePools, Labels, and Taints

In an MNG world, workload isolation is done at the node group level. You create one MNG with the label workload=critical-addons and the taint dedicated=critical-addons:NoSchedule, another MNG with workload=apps and dedicated=apps:NoSchedule, and your deployments declare a nodeSelector plus matching toleration so each pod lands on the right group.

The same model works on Auto Mode. You just express it through NodePool CRDs instead of node group configurations. The default general-purpose NodePool that Auto Mode ships with is a catch-all; for real isolation you create additional NodePools with their own labels, taints, and instance constraints, and your deployments use the same nodeSelectors and tolerations they used before.

Mirroring the three-MNG layout in Auto Mode

To replicate the kubernetes-components / critical-addons / apps layout, define three NodePools. Each gets its own label, taint, and instance constraints, exactly the way a node group used to.

# NodePool: kubernetes-components (CoreDNS, system tooling)
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: kubernetes-components
spec:
  template:
    metadata:
      labels:
        workload: kubernetes-components
    spec:
      nodeClassRef:
        group: eks.amazonaws.com
        kind: NodeClass
        name: default
      taints:
        - key: dedicated
          value: kubernetes-components
          effect: NoSchedule
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["on-demand"]
        - key: eks.amazonaws.com/instance-category
          operator: In
          values: ["t"]
        - key: eks.amazonaws.com/instance-size
          operator: In
          values: ["small", "medium"]
  limits:
    cpu: "8"
# NodePool: critical-addons (Prometheus, Loki, ALB controller, etc.)
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: critical-addons
spec:
  template:
    metadata:
      labels:
        workload: critical-addons
    spec:
      nodeClassRef:
        group: eks.amazonaws.com
        kind: NodeClass
        name: default
      taints:
        - key: dedicated
          value: critical-addons
          effect: NoSchedule
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["on-demand"]
        - key: eks.amazonaws.com/instance-category
          operator: In
          values: ["m", "r"]
  limits:
    cpu: "32"
    memory: "128Gi"
# NodePool: apps (stateless application workloads, Spot-enabled)
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: apps
spec:
  template:
    metadata:
      labels:
        workload: apps
    spec:
      nodeClassRef:
        group: eks.amazonaws.com
        kind: NodeClass
        name: default
      taints:
        - key: dedicated
          value: apps
          effect: NoSchedule
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: eks.amazonaws.com/instance-category
          operator: In
          values: ["m", "c"]
  limits:
    cpu: "200"
    memory: "800Gi"

A few things to notice:

  • The label on the NodePool template (workload: critical-addons) is applied to every node provisioned by that pool. Pods use this as their nodeSelector match.
  • The taint (dedicated=critical-addons:NoSchedule) is also applied to every node. Pods need a matching toleration or they will not schedule there. This is the part that excludes other workloads from the pool.
  • The requirements constrain instance shape: capacity type (Spot vs on-demand), category (t/m/c/r), size, architecture. Auto Mode picks the cheapest instance within these constraints when it needs to provision.
  • The limits stop the pool from running away. cpu: "200" means Karpenter will never let the pool exceed 200 vCPU across all nodes it provisions, regardless of pending pods.

Pod-side: same nodeSelector and toleration pattern as MNGs

The deployment side does not change. The exact YAML you used to pin a pod to the critical-addons MNG continues to work; the label key and taint key are just declared on a NodePool now instead of on a node group.

# Prometheus pinned to the critical-addons NodePool
apiVersion: apps/v1
kind: Deployment
metadata:
  name: prometheus
spec:
  template:
    spec:
      nodeSelector:
        workload: critical-addons
      tolerations:
        - key: dedicated
          operator: Equal
          value: critical-addons
          effect: NoSchedule
      containers:
        - name: prometheus
          image: prom/prometheus:latest
# Stateless app pinned to the apps NodePool
spec:
  template:
    spec:
      nodeSelector:
        workload: apps
      tolerations:
        - key: dedicated
          operator: Equal
          value: apps
          effect: NoSchedule

The label key (workload) and taint key (dedicated) are arbitrary, pick whatever your fleet already uses for MNGs and reuse the same names so existing deployments do not need to change. The migration is literally "rename one set of YAML resources, leave pod specs alone".

Disabling the default general-purpose NodePool

The built-in general-purpose NodePool that Auto Mode ships with is a catch-all: any untainted pod without a matching nodeSelector will land on it. That is convenient during early experimentation, but it breaks the isolation guarantee in production, a misconfigured deployment will silently schedule onto shared nodes instead of being pinned where you intended.

To remove the default and force every workload onto a specifically targeted NodePool:

# Disable the built-in general-purpose NodePool
aws eks update-cluster-config \
  --name apps-prod \
  --region eu-central-1 \
  --compute-config enabled=true,nodePools=,nodeRoleArn=$NODE_ROLE

Setting nodePools to an empty list keeps Auto Mode enabled but removes AWS's default NodePool. Now only the NodePools you defined can provision nodes. Workloads with no matching nodeSelector go Pending, which is exactly what you want in production: explicit scheduling, no fallback.

NodeClass: per-NodePool networking and IAM

The NodeClass resource is Auto Mode's equivalent of the community Karpenter EC2NodeClass. The default NodeClass named default covers most cases, all subnets in the cluster, the default node role, the default security group. Create custom NodeClasses when you need:

  • Different subnets per NodePool (e.g. apps on private app-tier subnets, critical-addons on a separate observability subnet).
  • Different IAM instance profiles per NodePool, so addon nodes do not get the same permissions as app nodes.
  • Different security groups, useful if Prometheus needs scrape access to extra targets that app nodes do not.
# Custom NodeClass for the apps NodePool
apiVersion: eks.amazonaws.com/v1
kind: NodeClass
metadata:
  name: apps-private
spec:
  role: AutoModeAppsNodeRole
  subnetSelectorTerms:
    - tags:
        kubernetes.io/role/internal-elb: "1"
        tier: apps
  securityGroupSelectorTerms:
    - tags:
        Name: apps-prod-apps-sg

Reference it from a NodePool with nodeClassRef.name: apps-private instead of default.

The mental shift: in MNGs you scaled node groups. In Auto Mode you describe constraints and let Karpenter provision. A NodePool is not a fixed fleet, it is a policy that says "if a pod matches my label/taint/requirements, provision the cheapest instance from this category, up to these limits." The pod-side configuration (nodeSelector plus toleration) is byte-for-byte identical to the MNG pattern, only the resource that publishes the label and the taint has changed.

Cost Implications

Auto Mode's pricing is the part most teams trip over, because the AWS pricing page reads like it is only about EC2 instances. There are actually three things you pay for, and one of them is a fee on top of compute.

What you pay for

  1. The EKS control plane, unchanged at $0.10/hour ($73/month) in eu-central-1. Same for self-managed, MNGs, and Auto Mode.
  2. The EC2 instances, billed at standard on-demand or Spot rates. Auto Mode does not give you a different rate card for EC2.
  3. The Auto Mode management fee, an extra per-second charge on each EC2 instance Auto Mode provisions. The fee is roughly 12% of the on-demand price of that instance family, and it applies to Spot too (i.e. the surcharge is on the on-demand price, not the discounted Spot price).

Other Auto Mode resources, EBS volumes, ELBs, are billed at the normal EBS and ELB rates with no separate surcharge. The 12% lives entirely on the EC2 line.

At this scale, the surcharge is the salary equivalent of a junior platform engineer per year. The trade-off becomes real. Auto Mode's consolidation, AMI patching automation, and removal of Karpenter operational toil need to be worth that. For most teams under 10 engineers, they are. For a 50-engineer platform org that has already built rock-solid Karpenter automation, the maths is closer.

FinOps rule of thumb: Auto Mode pays for itself when (a) your fleet has meaningful idle headroom that Karpenter consolidation can reclaim, (b) your team spends measurable hours per month on AMI patching, addon upgrades, and Karpenter version bumps, or (c) you are starting fresh and would otherwise need to build that automation. It is hardest to justify on already-optimised, large, mostly-static fleets.

Storage and load balancer costs are unchanged

Auto Mode provisions EBS volumes (gp3, $0.0952/GiB-month in eu-central-1) and ELBs (ALB at $0.02528/hour + LCUs, NLB similar) on your behalf, but those are billed at standard rates. There is no Auto Mode surcharge on storage or load balancers, the management fee is purely on EC2 compute.

Workload Considerations and Edge Cases

Most stateless application workloads, addons, and platform tooling fit Auto Mode without changes. A few categories need extra attention before you flip the switch.

GPU and ML workloads

Auto Mode supports GPU instance families (g5, g6, p5) the same way Karpenter does, you list them in the NodePool's instance-family requirements and Auto Mode provisions on demand. There are caveats:

  • Bottlerocket GPU AMI is what you get, not a custom CUDA image. For most inference and standard training workloads this is fine; the NVIDIA drivers and container runtime are pre-installed. If you have a deep-learning stack that depends on a specific CUDA version pinned to a custom AMI, Auto Mode is the wrong choice.
  • Quotas still apply. The 12% management fee on a p5.48xlarge at $98/hour list price is roughly $11.76/hour or ~$8,600/month extra per instance. For GPU-heavy fleets, the surcharge maths is dramatic. Many teams keep GPU workloads on a self-managed or MNG node group and only put CPU workloads on Auto Mode.
  • Time-slicing and MIG configurations need to be done at the pod level; you cannot pre-configure node-level GPU partitioning via custom userdata.

Windows containers

Auto Mode does not support Windows nodes. Stay on MNGs for Windows workloads.

Custom AMIs and bootstrap scripts

If your security team mandates a hardened internal AMI (CIS benchmark with custom audit daemons, internal certificates, FIPS modules), Auto Mode is not an option. Custom userdata, custom kubelet flags, custom CNI overrides, all locked down. Bottlerocket is the only OS, and its configuration is set by AWS.

HostPath, HostNetwork, and privileged workloads

Bottlerocket has a read-only root filesystem with a minimal package set. Workloads that mount arbitrary host paths, run as privileged with broad capability sets, or depend on packages being installed on the host (debugging daemons, eBPF tracers that need kernel headers) will hit walls. Most of them are anti-patterns anyway; the few legitimate cases (some service meshes, some observability agents) need to be tested before migration.

Daemonsets you can't replace

Auto Mode bundles its own VPC CNI, kube-proxy, CoreDNS, Pod Identity agent, and node monitoring agent. You cannot install a competing implementation on the same nodes (e.g. Cilium replacing VPC CNI, NodeLocal DNSCache layered on top of CoreDNS). If you depend on those, Auto Mode is not a fit until AWS adds the integration points.

Stateful workloads

Stateful sets work, the EBS CSI driver is built in and the default gp3 storage class is reliable. The 21-day node refresh interacts with PVCs the way Karpenter normally does: the new node is provisioned in the same AZ as the volume, the volume re-attaches. Make sure your stateful workload's PodDisruptionBudget tolerates a node drain, otherwise the 21-day refresh can stall.

Migrating from EKS Managed Node Groups to Auto Mode

The good news: Auto Mode can be enabled on an existing EKS cluster alongside your existing MNGs. You do not need a new cluster, you do not need a blue/green migration, you can let workloads drain to Auto Mode nodes gradually.

Phase 1 · Enable Auto Mode on the existing cluster

# Pre-flight: confirm cluster version supports Auto Mode
# Auto Mode requires EKS 1.29+. Upgrade first if needed.
aws eks describe-cluster --name apps-prod --region eu-central-1 \
  --query 'cluster.version'

# Enable Auto Mode on the existing cluster
aws eks update-cluster-config \
  --name apps-prod \
  --region eu-central-1 \
  --compute-config enabled=true,nodePools=general-purpose,nodeRoleArn=$NODE_ROLE \
  --kubernetes-network-config '{"elasticLoadBalancing":{"enabled":true}}' \
  --storage-config '{"blockStorage":{"enabled":true}}'

What this does:

  • Enables the managed Karpenter controller in the cluster.
  • Creates the default general-purpose NodePool, which provisions c, m, and r instance families across multiple AZs.
  • Enables the managed ALB controller (creates the eks-auto-alb IngressClass and the eks.amazonaws.com/nlb LoadBalancerClass).
  • Enables the managed EBS CSI driver and the default gp3 storage class.

Your existing MNGs are untouched. Their nodes keep running. Pods keep scheduling on them.

Phase 2 · Create custom NodePools that mirror your MNG layout

Before migrating any workload, define a NodePool for every MNG you intend to replace. Use the same label and taint keys/values that the MNGs use today, so deployments do not have to change their nodeSelector or tolerations. See the Workload Isolation section above for the full kubernetes-components / critical-addons / apps NodePool examples.

If you want strict isolation in production, disable the default general-purpose NodePool now so the only pools available are the ones you defined.

Phase 3 · Validate Auto Mode with a non-critical workload

Pick something low-risk: a dev namespace, a batch job, an internal tool. Deploy it with the same nodeSelector and toleration it already uses for its MNG, and confirm it lands on an Auto Mode node provisioned by the matching NodePool:

spec:
  nodeSelector:
    workload: apps
  tolerations:
    - key: dedicated
      operator: Equal
      value: apps
      effect: NoSchedule

Verify with kubectl get nodes -L karpenter.sh/nodepool,workload that the new node has the expected NodePool ownership. Confirm provisioning latency is in the expected ~60 second range, an ALB created via the new IngressClass works, and a PVC against the new gp3 storage class binds and mounts. If any of these break, you want to know now, not after you have migrated half your production traffic.

Phase 4 · Migrate workloads node group by node group

Work in reverse priority order, least critical first. For each MNG, in this order: apps → critical-addons → kubernetes-components.

  1. Cordon the MNG nodes. kubectl cordon every node in the target MNG so no new pods land on them.
  2. Roll the workload. kubectl rollout restart deployment/.... Because pods carry the same nodeSelector + toleration that the matching Auto Mode NodePool publishes, and the MNG nodes are cordoned, the new pods schedule onto Auto Mode nodes. No deployment YAML changes required.
  3. Watch placement. kubectl get pods -o wide should show new pods on Auto Mode nodes. If anything lands on a wrong node, double-check the NodePool's labels and taints match what the deployment selects.
  4. Drain and delete the MNG. Once the workloads are on Auto Mode, kubectl drain the old nodes, then delete the node group: aws eks delete-nodegroup --cluster-name apps-prod --nodegroup-name <name>.
  5. Wait a day before moving the next MNG. Let real traffic, weekday/weekend patterns, scheduled jobs, and any scheduled scale events hit the Auto Mode nodes before you commit further.

Phase 5 · Migrate the addons

This is where MNG migrations get fiddly. Your existing cluster probably has:

  • The AWS Load Balancer Controller installed via Helm.
  • The EBS CSI driver installed as an EKS managed addon.
  • The VPC CNI installed as an EKS managed addon.
  • CoreDNS and kube-proxy as EKS managed addons.
  • An external-dns / cert-manager / Prometheus stack that depends on the above.

Auto Mode brings its own. Two coexisting installations of the AWS Load Balancer Controller will fight over ingress reconciliation. The fix:

  1. Migrate Ingresses one at a time. Each Ingress lists an ingressClassName. The legacy Helm controller watches its own class (alb). The managed Auto Mode controller watches eks-auto-alb. Update Ingresses to the new class, confirm a new ALB is created and DNS swung over (Route 53 weighted records work well here), then delete the old ALB.
  2. Migrate Services of type LoadBalancer by switching their loadBalancerClass to eks.amazonaws.com/nlb.
  3. Once no resources reference the legacy classes, uninstall the Helm controller release.
  4. Repeat for EBS CSI. The legacy addon and the Auto Mode driver coexist, but you should remove the legacy EKS managed addon once all PVCs are using the Auto Mode storage class.
  5. Disable the legacy CoreDNS, kube-proxy, and VPC CNI addons only when no MNG nodes remain in the cluster, since Auto Mode's managed versions only run on Auto Mode nodes.

Phase 6 · Decommission

Once every workload runs on Auto Mode nodes and every addon has been migrated to its Auto Mode equivalent:

  • Delete the last MNGs.
  • Delete the legacy IAM roles, ASGs, launch templates that the MNGs created.
  • Delete the legacy Helm releases (LB controller, anything else replaced).
  • Delete the legacy EKS managed addons (EBS CSI, CoreDNS, kube-proxy, VPC CNI).
  • Verify your Terraform / CDK / Pulumi state matches reality, the cluster definition should now contain Auto Mode flags and NodePool CRDs, nothing else.

Migrating from Self-Hosted Karpenter to Auto Mode

If you have already done the work to move from MNGs to self-hosted Karpenter, the migration to Auto Mode is shorter, but there are gotchas because both Karpenters run inside the same cluster during the transition.

The core problem: two Karpenters, one cluster

Self-hosted Karpenter uses the community CRDs: NodePool (group karpenter.sh) and EC2NodeClass (group karpenter.k8s.aws). Auto Mode uses a different CRD set: NodePool (group karpenter.sh, same name and group) and NodeClass (group eks.amazonaws.com, different from EC2NodeClass).

The NodePool resource is shared between both, which means a single NodePool can only be claimed by one of them. They distinguish ownership by inspecting the NodePool's spec.template.spec.nodeClassRef:

  • If nodeClassRef.group is karpenter.k8s.aws, the community Karpenter handles it.
  • If nodeClassRef.group is eks.amazonaws.com, Auto Mode handles it.

This is the lever you use during migration: keep your existing NodePools pointing at EC2NodeClass, create new NodePools pointing at the Auto Mode NodeClass, and let workloads shift between them.

Phase 1 · Enable Auto Mode alongside self-hosted Karpenter

aws eks update-cluster-config \
  --name apps-prod \
  --region eu-central-1 \
  --compute-config enabled=true,nodePools=general-purpose,nodeRoleArn=$NODE_ROLE

This creates the default general-purpose NodePool managed by Auto Mode. Your existing Karpenter NodePools continue to provision EC2NodeClass nodes alongside it.

Phase 2 · Identify mutually exclusive workloads

To stop both Karpenters from competing for the same pending pods, use taints on the Auto Mode NodePool that only the workloads you want to migrate tolerate. Auto Mode nodes do not get the karpenter.sh/registered=true label that self-hosted Karpenter sets, so node-affinity rules referencing that label naturally keep workloads on self-hosted nodes until you change them.

# Auto Mode NodePool with a taint that opt-in workloads tolerate
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: auto-mode-pool
spec:
  template:
    spec:
      nodeClassRef:
        group: eks.amazonaws.com
        kind: NodeClass
        name: default
      taints:
        - key: workload
          value: auto-mode
          effect: NoSchedule

Phase 3 · Migrate workloads NodePool by NodePool

  1. Start with a non-critical NodePool's workloads. Add the toleration to those deployments. Roll them. They schedule on Auto Mode nodes.
  2. Once the old self-hosted NodePool has no pods, scale it to limits.cpu: 0 so Karpenter stops provisioning new nodes for it, and let the existing nodes drain via consolidation or expiration.
  3. Repeat per NodePool, leaving the system / addons NodePool for last.

Phase 4 · Migrate the addons that lived on self-hosted Karpenter

The big one is Karpenter itself. The self-hosted Karpenter controller pod runs somewhere, often on a small MNG you kept around for system pods, or on the Karpenter-managed nodes themselves. You cannot delete it while it is still managing nodes. The sequence:

  1. Migrate every workload to Auto Mode NodePools.
  2. Delete every self-hosted Karpenter NodePool (the ones with EC2NodeClass refs). Karpenter will deprovision the nodes it provisioned.
  3. Helm uninstall the Karpenter release.
  4. Delete the Karpenter CRDs (EC2NodeClass is no longer in use), and the IAM role / SQS interruption queue / EventBridge rules that Karpenter created.
  5. Migrate the AWS Load Balancer Controller, EBS CSI, CoreDNS, kube-proxy, and VPC CNI the same way as in the MNG-to-Auto-Mode flow, since those are also replaced by Auto Mode managed versions.

What to watch during the Karpenter migration

Signal What to watch Action
Pending pods Should drain within ~60s on either NodePool If they pile up on the wrong side, check tolerations
Node count drift Self-hosted nodes count drops as Auto Mode rises Use kubectl get nodes -L karpenter.sh/nodepool to track per-pool
Cost line on Cost Explorer EC2 cost roughly flat, Auto Mode line appears Tag NodePools so the split is visible
Spot interruption recovery Auto Mode pre-provisions like community Karpenter No action, verify on next interruption event
ALB / NLB churn Switching IngressClass replaces the load balancer Use Route 53 weighted records to swing traffic, not in-place swap
Don't skip the parallel-running phase. Whether you are coming from MNGs or from self-hosted Karpenter, run both side by side for two to four weeks before deleting the legacy installation. The cost of running both is a handful of euros per month; the cost of discovering a workload-specific incompatibility after you have already deleted the safety net is much higher.

When Auto Mode Is the Wrong Choice

Auto Mode is not a universal upgrade. Skip it when any of these apply:

  • Custom AMI requirements. CIS-hardened internal builds, FIPS modules, regulated environments that demand AMI control.
  • Windows containers. Not supported.
  • Specialised CNI. Cilium, Calico, or any CNI that replaces VPC CNI rather than layering on top.
  • Custom kubelet configuration. Reserved system resources, eviction thresholds, log rotation, anything you set via kubelet flags or config files.
  • SSH / SSM debugging is part of your incident response. Bottlerocket is API-only; debugging is via kubectl, logs, and the Bottlerocket control container, not shell access.
  • You have already invested deeply in Karpenter ops. If your team has built dashboards, runbooks, drift policies, and consolidation tuning for self-hosted Karpenter, the 12% surcharge buys very little additional value.
  • GovCloud or restricted environments. Auto Mode availability in GovCloud and isolated regions lags behind commercial regions, check before planning.
  • GPU-heavy fleets at scale. The 12% fee on p5 and g6e instances is brutal at production scale. Consider keeping GPUs on MNGs.

The Decision Framework

Skip the feature list and ask in order:

  1. Do you have non-negotiable AMI, CNI, or kubelet customisation requirements? → MNG or self-managed. Auto Mode is not flexible enough.
  2. Are you starting a new EKS cluster? → Auto Mode. The simplest possible production-grade EKS today.
  3. Is your team small (under ~10 platform engineers) and is "stop maintaining Karpenter" a stated goal? → Auto Mode. The 12% buys back real engineering hours.
  4. Do you already have a healthy, optimised self-hosted Karpenter setup? → Stay on it. Re-evaluate when your platform team shrinks or when AWS reduces the management fee.
  5. Are you running heavy GPU workloads? → Hybrid. Auto Mode for CPU workloads, MNG or self-managed for GPU nodes.
  6. Are you locked into a specific Karpenter version or feature ahead of AWS's managed rollout? → Stay on self-hosted Karpenter for now.

Key Takeaways

  1. Auto Mode is managed Karpenter plus managed addons. Same Kubernetes API, same NodePool model, but AWS runs Karpenter, the LB controller, the CSI driver, the CNI, kube-proxy, and CoreDNS as a single managed unit.
  2. The 12% surcharge is the headline cost. Applied to every EC2 instance Auto Mode provisions, on top of the standard on-demand or Spot price. At small scale it is noise. At 50+ nodes it is a real FinOps line item.
  3. Whether it is cheaper or more expensive depends on your current consolidation. If your MNGs run hot and lean, Auto Mode is a 9-12% premium. If your MNGs are sized for peak with idle headroom, Auto Mode's Karpenter consolidation will more than pay for the fee.
  4. Bottlerocket is non-negotiable. No SSH, no SSM, no custom AMI. Workloads that need host access, custom packages, or specialised CNI are not Auto Mode candidates.
  5. GPU workloads need a separate decision. The 12% on a p5.48xlarge is several thousand euros a month per instance. Hybrid setups, Auto Mode for CPU plus MNGs for GPU, are common.
  6. You can migrate gradually from either MNGs or self-hosted Karpenter. Both legacy and Auto Mode run side by side. Use taints, tolerations, and NodeClass references as the routing layer during migration. Plan two to four weeks of overlap before deleting the legacy installation.
  7. For new clusters and lean platform teams, Auto Mode is the new default. The cost of building MNG plus Karpenter plus addon automation from scratch outweighs the surcharge, almost always.
